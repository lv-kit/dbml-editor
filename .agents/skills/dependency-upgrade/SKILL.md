# 依存の更新と非推奨の是正

## モード判定

どちらの入り口かで読む reference が変わる。**該当する側だけを読む。**

| 状況 | 読むもの |
|---|---|
| リファクタ・既存コードの手入れの最中 | `references/deprecation.md` だけ |
| バージョンを上げる依頼 | `references/upgrade.md` → その最終ステップで `references/deprecation.md` |

バージョンアップは必ず `upgrade.md` から入る。基準を決めずに上げ始めると、あとから範囲を戻せない。

## 対応言語

`deprecation.md` の一次シグナル表と `upgrade.md` の制約表は、次の5系統を扱う。

| 系統 | 依存定義 |
|---|---|
| Python | `pyproject.toml` / `requirements.txt` |
| TypeScript / JavaScript | `package.json` |
| PHP | `composer.json` |
| Dart / Flutter | `pubspec.yaml` |
| Rust | `Cargo.toml` |

表に無い言語でも、考え方（一次シグナルを先に見る、触った箇所だけ直す、連鎖の根拠を残す）は同じ。その言語の型チェッカ・linter が非推奨をどう報告するかを調べてから進める。

## 是正の範囲

**触った箇所だけ**を直す。変更する関数・行が呼んでいる非推奨 API が対象で、同じファイルの他の箇所は含めない。

自動修正ツール（`dart fix --apply`、Rector など）は指定範囲に一括で効くため、素で使うとこの範囲を破る。使う場合の手順は `deprecation.md` に書いてある。

## 対話できない環境での扱い

ヘッドレス実行（agy への委譲、`claude -p`、CI）ではヒアリングを**しない**。質問リストを返しても誰も答えられない。

1. 呼び出し元の指示に基準が書かれていれば、それに従う
2. 無ければ既定を適用する。**セキュリティ修正のみ / メジャー跨ぎなし / 連鎖は周辺ライブラリまで**
3. どちらの場合も、**採用した基準を成果物（PR 本文・コミットメッセージ・報告）に明記する**

既定を適用した結果、目的のバージョンに届かないことがある。それは失敗ではなく、基準を上げる判断をユーザーに戻すべき状態として報告する。
