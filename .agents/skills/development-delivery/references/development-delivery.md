## 開発ワークフロー: 完了〜PR

development-workflow の実行手順4以降（完了報告、レビューと修正のループ、コミット・push・PR・CI・PRコメント確認）と、Worktreeの後始末を定める。手順1〜3（着手〜実装）は development-workflow にある。

### 実行手順（完了〜PR）

4. 完了時は `git diff --stat` と検証結果を示す。レビューへ回せるクリーンな差分を保つ（無関係な変更を混ぜない、フォーマットのみの変更と機能変更を分ける、一時ファイルを残さない）。
5. レビューは今回の変更だけを対象に、仕様逸脱、バグ、回帰（既存機能の破損や指示外の挙動変更）、セキュリティ、テスト不足、プロジェクト規約違反を確認する。**回帰・デグレチェックは、①変更前の挙動と比較して変更対象を呼び出す既存コードや依存箇所に意図しない挙動変化や既存機能の破損がないか、②指示されていない挙動変更（スコープ外の暗黙の仕様変更や副作用）が含まれていないか、を重点的に判定する。** 差分に依存バージョンの変更（lock ファイル・依存定義の更新）が含まれる場合は、`dependency-upgrade` スキルの手順どおり公式リリースノート/CHANGELOGが確認され、挙動変化リスクが報告に記載されているかも確認する。指摘には根拠、影響、再現または確認方法を付ける。好みや任意改善は不合格にしない。L0はテスト・lintの結果で足りる場合、独立レビューを必須としない。L1は独立した軽量Reviewer、L2/L3は `orchestration/routing.yaml` のreviewルートに一本化したReviewer、L4は `workflow-security-reviewer` を使う。L3以上かつ差分規模が大きい場合は、`large_review` ルート（Claude Codeの `workflow-large-reviewer`）を通常のreviewルートに代えて使ってよい。
6. 指摘をブロッキングと非ブロッキングに分類し、修正と再レビューを繰り返す。修正（FB対応）は内容に応じて `Gemini 3.8 Flash / medium` またはClaude Sonnet 5.5 / mediumを使う。
   - **ブロッキング**（バグ / 回帰・デグレ・指示外の挙動変更 / セキュリティ / 仕様逸脱、テスト不足、および挙動や安全性に影響しうる規約違反）は、解消するまで回数上限なしで修正と再レビューを繰り返す。
   - **バージョンアップに伴う挙動変化リスク**（公式リリースノート/CHANGELOGで確認された、既存機能を壊しうる変更）もブロッキングとして扱う。解消手段はコード修正・テスト追加に限らず、**ユーザーが変更の受け入れを明示的に承認すること**でもよい。上流が意図した仕様変更まで無理にコードで吸収しない。
   - **非ブロッキング**のうち、今回の変更と直接関係し、同一PRで安全に完結できる内容は、そのまま修正して検証する。
   - **非ブロッキング**のうち、今回の変更から独立して別PRで問題ない内容は、リモートがあり `gh` を利用できる場合に1件ずつ別Issueを作成する。Issueタイトルの先頭には `[<base>]` の形でベースブランチ名を付ける。既存PRを更新中ならそのPRの実際のベースブランチを使い、PR未作成ならこの後の手順7と同じ基準（`develop` があればそれ、無ければリモートのデフォルトブランチ（`origin/HEAD`））で前倒しに定める。Issueを作れない環境（git管理外、リモート無し、`gh` 不可）では、PR本文または最終報告に列挙する。
   - 好みだけの提案や根拠のない任意改善は、修正もIssue化もしない。
   - **同一のブロッキング指摘が3周連続で解消しない**場合は繰り返しを止め、エスカレーションしてユーザーの判断を仰ぐ。この場合、手順7は実行しない。
   - **PR前ゲート**: PRのレビュアーがCodex（GitHub連携）のリポジトリでは、最初のpushの前に、未コミットの変更（未追跡の新規ファイルを含む）は `codex review --uncommitted`、コミット済みの差分は `codex review --base <base>` でローカルレビューし、脅威モデルの範囲内またはブロッキングに分類されるP0/P1/P2が0件になるまで修正と再実行を繰り返す。Issue化済みの範囲外指摘と、根拠のない任意改善は残ってよい。`--uncommitted` が未追跡ファイルを含むことはCLIのhelpに明記されているが、`--base` が含むことは保証されていない。そのため新規ファイルがある間は `--uncommitted` を使い、コミット済みの差分と未コミットの変更が混在する場合は両方のコマンドを実行する。`routing.yaml` のreviewルートでの独立レビューは従来どおり行い、このゲートはその追加として扱う。`codex` CLIが利用できない場合は、reviewルートにadversarial観点（「迂回・境界値・兄弟ケースを列挙して探す」）を明示して代替し、PR本文に代替した旨を書く。
   - **クラス単位で直す**: 指摘を修正するときは、指摘された1ケースだけでなく同じクラスの兄弟ケース（同じコマンド・関数の他のオプション、同種の入力形）を洗い出し、まとめて修正してテストへ追加してから次へ進む。1指摘1修正を繰り返してpushしない。
   - **pushはまとめる**: 指摘への対応は、ローカルで再レビューして新しい指摘が出なくなってからpushする。pushのたびにCodexの再レビューが走り、往復が増えるため。
   - **脅威モデル外の強化はIssue化する**: 対象に脅威モデルが文書化されている場合（例: hookは `README.md` の「hookの脅威モデル」）、その範囲外の強化指摘は同一PRで直さず、Issue化して根拠を返信する。範囲内のP1はブロッキングとして直す。
 7. ブロッキング指摘がなければ、コミット → push → PR 作成または更新を一続きで実行する。規模を問わず適用する。
   - コード修正または文章内容の修正を行った場合は、対象リポジトリでのPR作成または既存PRの更新と、PRコメントの妥当性チェックを必ずセットで実施する。PRコメントがない場合も、確認した結果を完了条件に含める。
   - PRに対する指摘を修正する場合は、同一PRのhead branchへコミットして当該PRに追加する。今回のスコープを超える内容は変更に混在させずIssue化する。ただし、同一PRで対応しないことがブロッキング要素になる場合は、スコープを超えていても対応し、同一PRに追加する。
   - ユーザーの停止指示がない限り、この一連の操作に追加承認は求めない。
   - ループ完結後に1コミットへまとめる（ループ中はコミットしない）。手順4 の分割規定は引き続き適用する。
   - 既存 PR の修正対応中は、その PR の head branch へコミットして PR を更新する（新規 PR を作らない）。
   - PR が未作成の作業ブランチで継続作業している場合は、そのブランチへコミットして PR を作成する（新しくブランチを切り直さない）。
   - base ブランチ上、または今回の作業と無関係なブランチにいる場合だけ、base から作業ブランチを切る。base は `develop` があればそれ、無ければリモートのデフォルトブランチ（`origin/HEAD`）。
   - CI が設定されているリポジトリでは、ブランチ作成、コミット、push、PR 作成を一続きで行い、CI が成功するまで対応する。
   - PR 作成済みのブランチを修正した場合は、修正後のコミット、push、CI 成功確認までを一続きで行う。
   - PR は ready で作成する。PR 本文は毎回、現在の差分全体を反映した内容へ書き直す。ただし本文が直前に生成した内容と一致しない（＝手動で編集されている）場合は上書きせず、ユーザーに確認する。
   - Claude Code（デスクトップアプリ）では、PR作成または更新の直後に、`ccd_pr` の `get_status` で対象PRが束縛済みか確認し、未束縛なら `bind_pr` で束縛したうえで、`set_monitor` で `auto_fix` を常に有効にする（`address_comments` は `auto_fix` と同じ値にする）。すでに有効なら変更しない。Auto-fixはCI失敗・マージコンフリクト・レビューコメントでセッションを起こす機能であり、PRコメントの取得・確認とCI待機を省略する根拠にしない。auto-mergeは有効にしない。`ccd_pr` ツールが無い環境ではこの項目を適用しない。
   - PR の本文、コメント、更新内容は必ず日本語で記載する。
   - 修正の発生や、CI 失敗への修正など、PR の更新が必要な変更があれば、必ず PR を更新する。
   - PR 作成後またはPRチェック時にPRコメント（レビューコメント、レビュー本文、CI botの指摘を含む）が存在する場合は、各コメントを仕様、差分、再現条件、既存規約およびテスト結果と照合して妥当性を確認する。妥当な指摘は必ず、修正、テスト追加、説明またはPR更新のいずれかで対応し、対応結果をPRへ日本語で記載する。妥当でない指摘は根拠を示して対応不要と説明する。対応後は該当コメントと関連する回帰への再確認を行い、未確認・未対応のコメントを残したまま完了扱いにしない。
   - CIの有無やBilling問題にかかわらず、Claude Codeを含むすべての実行環境で、PR作成または更新後にPRコメントを取得して確認することを完了前の必須ゲートとする。レビューやCIの非同期コメントが後から追加される場合があるため、取得時点でコメントがなくても確認を省略せず、未確認・未対応のコメントがないことを確認するまで完了扱いにしない。
   - PR作成・更新後にレビューまたはCIが実行中の場合は、終端状態になるまで待機してからPRコメントを再取得する。指摘への対応でpushした場合も、同じ待機と再取得を繰り返す。待機がタイムアウトした場合は完了扱いにせず、原因と再実行主体を報告してエスカレーションする。
   - CI が設定されているリポジトリでは、PRまたはブランチで実行された必須CIを待機する。失敗が今回の変更に起因する場合は、修正、再検証、commit、pushを行って再び待機する。必須CIがすべて成功するまで完了扱いにしない。
   - CI基盤障害、権限不足、外部サービス障害などコードで解消できない失敗は、原因、確認結果、再実行が必要な主体を報告し、成功とは扱わない。
   - CIがBilling問題（利用枠超過、支払い停止等）で実行できない場合は、Dockerを含む必要なテストをローカルで成功させ、PRコメントを取得・妥当性確認・対応したことを確認したうえで、CI待機をスキップし、その旨と原因を報告して、CI失敗を無視してマージする。それ以外のCI失敗は無視しない。
   - Issueに対応する作業は、PR作成 → PRコメント対応 → マージまでを一続きで実施する。PRコメントの取得・妥当性確認・対応、必須CIの成功（Billing問題を除く）、未対応コメントなしを確認したら、追加承認なしでマージする（`gh pr merge`）。マージ後は「Worktreeの後始末」に進む。auto-mergeは有効にしない。ユーザーの停止指示、ブロッキング指摘の残存、CIの失敗（Billing問題以外）がある場合はマージしない。
   - コードを変更したら必ずPRを作成する。変更内容が既存のオープンなPRに含められる（同じ目的・スコープで、head branchへ追加しても差分とレビューが混在しない）場合は、新規PRを作らず、そのPRのhead branchへコミットして統合してよい。
   - デプロイ作業以外のCI（リント、テスト、型チェック、ビルド検証など）は新規に作らない。これらはローカルで実施し、PR作成前に成功させる。CIを作るのはデプロイ作業に限る。既存のデプロイ以外のCIは、ユーザーの指示なしに削除しない。

### Worktreeの後始末

作業に使った git worktree は、次の完了条件を満たした直後に自動削除する。削除は作業中のworktree自身ではなく、親worktreeまたは別の安全なworktreeから実行する。完了条件は次の優先順位で判定する。

- CIが設定されている場合: PRまたはブランチで実行された必須CIが成功した後、またはCIがBilling問題で実行できず、必要なローカルテストの成功とPRコメントの確認・対応を完了したうえで完了扱いとした後。ブランチを切り替えない作業でも、この条件を優先する
- CIが未設定で、ブランチを切り替えない作業の場合: コミットとプッシュが完了した後
- CIが未設定で、それ以外の場合: PRを作成した後

削除前に `git worktree list` で対象パスと状態を確認し、`git worktree remove`（必要なら `--force`）を実行する。削除後も `git worktree list` で対象が残っていないことを確認する。CI失敗、PR作成失敗、プッシュ失敗、未コミット変更、または完了条件を満たさない場合は削除しない。

`EnterWorktree`/`ExitWorktree` 経由・素の `git worktree add` 経由を問わず適用する。自分（Claude Code）が作成したworktreeに限らず、Codex・Gemini（agy/Antigravity）・Grok等、他のAIエージェントや外部CLIが作成したworktreeも削除対象に含める。ただし、他エージェントが**現在進行中**の作業である疑いがある場合（該当ブランチに直近のコミット・未コミット差分がある、他セッションが動作中と分かっている等）は削除せず、状況を確認してユーザーへ確認する。ユーザーが明示的に「残しておいて」と指示した場合も削除しない。
