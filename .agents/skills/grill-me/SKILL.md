# grill-me

ユーザーが `/grill-me`、`$grill-me`、または設計・要件・計画の壁打ちを求めた場合、
実装には進まず、まず合意形成のための対話型インタビューを開始してください。

## 動作ガイドライン

1. **徹底的なインタビュー**
   - 設計案、プロジェクト計画、新機能の要件について、共通理解に達するまで執拗に質問してください。

2. **依存関係の解決**
   - 設計樹形の各分岐を1つずつ辿り、上流の論点から順に意思決定の依存関係を解決してください。

3. **1問ずつの質問**
   - ユーザーが回答しやすいよう、質問は必ず一度に「1つ」だけ投げかけてください。

4. **選択肢と推奨回答の提示**
   - 回答空間が列挙可能な質問では、必ず 2〜4 個の具体的な選択肢（A/B/C 形式）を提示し、そのうち 1 つに「推奨」マークと一行の理由を付けてください。
   - 理由は一般論ではなく、コードベース調査で得た根拠（既存パターン・スタック・プロジェクト規約）に基づくこと。
   - 各選択肢には「それを選ぶと何がどう変わるか」（スコープ・リスク・検証方法への影響）を添え、ユーザーがラベルではなく結果を選べるようにしてください。
   - 数値・URL・認証情報など本当に自由回答の質問では、無理に偽の選択肢を作らないでください。

5. **コードベースの優先探索**
   - 技術スタック、既存責務、型、API、テスト、ディレクトリ構造など、コードベースやドキュメントから分かることは、ユーザーに聞く前に調べて自己解決してください。
   - 調査で既に否定された選択肢を提示しないでください。
   - `.claude/**` や `.codex/**` は一括で読まず、まず `CLAUDE.md`（Codex では `AGENTS.md`）を読み、対象に応じた正本だけを参照してください。

6. **コード作成の制限**
   - 設計・要件・スコープ・完了条件の合意が取れるまで、実装コードの書き込みや PR 作成は行わないでください。

## 進め方

### テーマが未指定の場合

まず対象テーマを1問だけ確認してください。

```text
まず、今回 grill-me したいテーマを1つ教えてください。

推奨: 「<対象機能>について、実装前に要件と完了条件を固めたい」のように、
対象・目的・不安な点を短く書くと進めやすいです。
```

### テーマが指定されている場合

指定されたテーマに関係する既存情報を必要最小限で探索し、分かったことを短く要約してから、
最初の質問を1つだけ提示してください。

質問は原則として以下の順に進めます。

1. 解きたい問題・ユーザー価値
2. 対象ユーザー・利用シーン
3. スコープ内 / スコープ外
4. 既存仕様との整合
5. データ・API・認可・DB 影響
6. UI / UX / エラーハンドリング
7. テスト・検証方針
8. 完了条件
9. 実装タスク分解

## 質問の例

**良い例（1問ずつ・選択肢と推奨つき）:**
> Q: 通知の既読状態はどこで管理しますか？
> - A) `Notification.read_at`（nullable timestamp）を追加 — 推奨: 既読=NOT NULL で表現でき、別テーブルより単純でこの規模では十分。マイグレーション1本で済む
> - B) 既読管理の中間テーブルを新設 — 複数ユーザーへの同報通知が要件になる場合のみ有利。スキーマ・API とも変更範囲が広がる

**悪い例（複数質問を一度に投げる）:**
> Q: 通知の既読状態の管理方法、削除の可否、既読済み通知の保持期間、一覧APIのページネーション方式を教えてください。

## 終了条件

未確定事項リストが空になったら、以下の形式で「合意サマリ」を提示してユーザーの最終確認を取ってください。

```text
## 合意サマリ

### 決定事項
- 目的:
- スコープ:
- スコープ外:
- 主要な設計判断:
- 影響範囲（データ・API・認可・DB）:
- テスト方針:
- 完了条件:

### 検討したが却下した案
- ...（却下理由も添える）

### 未決事項（実装中に判断）
- ...

推奨: この内容で実装計画に進みます。変更したい点があれば、実装前にここで直しましょう。
```

確認が取れたら実装計画（`/plan`）にハンドオフする。このスキル自体は実装計画を作らない
（`CLAUDE.md` / `AGENTS.md` の「計画なしに実装しない」に接続する）。

## 禁止事項

- 合意前に実装コードを書く
- 一度に複数の質問を投げる
- コードベースで確認できる内容をユーザーに丸投げする
- 曖昧な完了条件のまま実装へ進む
- DB 変更、認可変更、API 変更の影響確認を省略する
