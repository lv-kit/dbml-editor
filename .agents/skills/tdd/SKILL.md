# TDD（テストファースト）

red → green のループで、残す価値のあるテストを作る。実装コードを書く前に、失敗するテストを先に書いて失敗を確認する。

## 前提

- テスト基盤（フレームワーク・実行コマンド）は既存のものを使う。既存コードとテストを読んでから書き始める（`core-rules`）。
- テストの置き場所・命名・ヘルパーはプロジェクトの既存規約が優先。
- 用語はプロジェクトの用語集（`GLOSSARY.md` 等があれば）とドメイン語彙に合わせる。

## 1. 先にシーム（テスト境界）を決める

シームは、内部に触れず挙動を観測できる公開境界（関数・API・コンポーネント・CLI）。テストはシームだけに置く。

- 最初のテストを書く前に、対象シームを列挙して提示し、ユーザーの合意を得る。合意前のシームにテストを書かない。
- 全パターンは網羅できない。重要経路と複雑なロジックに集中させるためにシームを絞る。
- 対話できない環境では、採用したシームを成果物に明記する。
- バグ修正のシームは、バグが観測される最上位の公開境界にする。

## 2. ループ（1サイクル = 1テスト → 1実装）

1. **RED**: 1つの挙動を表す最小のテストを書く。名前は「何ができるか」を書く（HOW を書かない）。
2. **RED確認（必須）**: 実行して失敗を見る。確認事項は次のとおり。
   - 失敗している。テスト自体の誤り（構文エラー、誤った import、typo）で落ちている場合は先に直す。未実装の関数・型を参照するコンパイルエラー・型エラーは、型検査言語では想定どおりの RED として扱ってよい。スタブを足すのは、このコンパイルエラー・型エラーを RED として観測した後に限る。足すのはコンパイルを通すための宣言だけの最小スタブ（挙動を持たない）とし、足した後にもう一度実行して、アサーションが想定どおり失敗することを確認する
   - 失敗メッセージが想定どおり
   - 機能が無いから失敗している（テストの typo ではない）
   - 最初から通る場合は既存挙動を試しているだけ。テストを直す。
3. **GREEN**: テストを通す最小のコードだけ書く。次のテスト用の先回り実装や、設定項目・汎用化を足さない。
4. **GREEN確認（必須）**: 対象テストが通ること、既存テストが壊れていないこと、警告やエラー出力が増えていないことを確認する。落ちたらコードを直す（テストをコードに合わせて緩めない）。
5. 次の挙動へ。1に戻る。

### 縦切りで進める（水平スライス禁止）

全テストを先にまとめて書いてから実装に入らない。想像上の挙動を検証する「形だけのテスト」になり、実装で得た学びが次のテストに反映されない。1テスト → 1実装を繰り返し、各テストを前サイクルの学びに応えるトレーサーブレットにする。

### バグ修正

1. 再現テストを書き、バグ内容どおりに失敗することを確認する（RED確認）。
2. 最小の修正で通す。
3. 修正を戻すとテストが再び落ちることを確認できるなら、確認する。

再現テストは原因調査の手段として原因が不明でも書いてよい。ただし、原因が分かる前に推測で本番コードを修正しない。

## 3. 良いテスト

テストは公開インターフェース経由で挙動を検証する。内部を全面的に書き換えてもテストは変わらない。良いテストは仕様書のように読める。

- 利用者・呼び出し側が気にする挙動を検証する。公開APIだけを使う。
- 1テストにつき論理的な検証は1つ。
- 内部構造をリファクタしてもテストが落ちない。

```typescript
// 悪い: 実装詳細に結合（内部協調オブジェクトのモック・呼び出し検証）
test("checkout calls paymentService.process", async () => {
  await checkout(cart, payment);
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total);
});

// 良い: 観測可能な挙動を検証
test("user can checkout with valid cart", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

```typescript
// 悪い: インターフェースを迂回して検証（DB を直接クエリ）
test("createUser saves to database", async () => {
  await createUser({ name: "Alice" });
  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});

// 良い: インターフェース経由で検証
test("createUser makes user retrievable", async () => {
  const user = await createUser({ name: "Alice" });
  expect((await getUser(user.id)).name).toBe("Alice");
});
```

## アンチパターン

- **実装結合**: 内部協調オブジェクトのモック、private メソッドのテスト、副経路での検証（DB 直接参照）。見分け方は、挙動が同じなのにリファクタでテストが落ちること。
- **同語反復（tautological）**: 期待値を実装と同じ方法で再計算するため、構成上必ず通る。期待値は独立した情報源（既知のリテラル、手計算した具体例、仕様）から取る。

```typescript
// 悪い: 期待値が実装と同じ計算
const expected = items.reduce((sum, i) => sum + i.price, 0);
expect(calculateTotal(items)).toBe(expected);

// 良い: 独立した既知のリテラル
expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
```

- **水平スライス**: 上記「縦切りで進める」を参照。
- **コール回数・順序の検証**: 挙動が同じでも内部実装の変更で落ちる。外部境界との契約として必要な場合だけ使う。

## モックの方針

システム境界だけをモックする。

- 対象: 外部API（決済・メール等）、時刻・乱数、DB（可能なら実テストDBを優先）、ファイルシステム（必要なときだけ）
- 非対象: 自分たちのクラス・モジュール、内部協調オブジェクト、自分で制御できるもの

境界は、モックしやすい形で設計する。

- 外部依存は内部で生成せず、引数や注入で渡す（例: `processPayment(order, paymentClient)`）。
- 汎用 `fetch` ラッパーより、操作ごとの関数（`getUser` / `createOrder` 等）を用意する。モックが1つの形を返すだけで済み、テスト内の条件分岐が不要になる。

## ループのルール

- **RED前にGREENなし**: 失敗するテストを見る前に実装を書かない。先に実装を書いてしまった場合は、その実装を一度外してテストを書き、RED確認してから戻す。
- **1サイクル1シーム・1テスト・最小実装**。
- **リファクタはループの外**: GREEN確認後の整理は、挙動を変えず、GREENを保ったまま別の手順として行う。今回の変更の範囲外のコードは整理しない（`core-rules`）。
- テストが通らないからといって、linter・型チェック・テスト設定を緩めない。

## 完了時の報告

- 採用したシームと、各サイクルの RED / GREEN 確認の結果
- 追加したテストと、実行した検証コマンド
- 実行できなかった検証とその理由
