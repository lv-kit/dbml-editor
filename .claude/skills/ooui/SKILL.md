# オブジェクト指向UI（OOUI）

UI は**必ず** OOUI で設計する。除外4類型に該当しない限り例外はない。

## このスキルが解く問題

タスク指向UI（機能ごとに画面を割る設計）は、機能が増えるたびに画面が増え、利用者は「やりたいことがどのメニューにあるか」を探し続けることになる。実装側も「登録画面」「編集画面」「一覧画面」が別コンポーネントに分裂し、同じデータの表示ロジックが3箇所に重複する。

OOUI は**オブジェクト（名詞）を先に決め、操作をその上に載せる**。利用者は「対象を選んでから、何をするか決める」という現実世界と同じ順序で操作でき、実装側もオブジェクト単位でコードがまとまる。

判定の軸はひとつ。**画面がオブジェクトを表しているか、機能を表しているか。**

## 適用範囲

以下すべてに適用する。

| レイヤー | 適用対象 |
|---------|---------|
| 情報設計 | 画面構成、画面遷移、ナビゲーション/メニュー構造 |
| ルーティング | URL パス、ルートディレクトリ構造 |
| 実装 | コンポーネント名、ファイル名、型名、ディレクトリ構造 |
| 上流文書 | PRD の UI 記述、ストーリーマップからのオブジェクト抽出（`pdm-prd` / `pdm-discovery` を参照） |

プラットフォームは問わない。Next.js（App Router）、Flutter、Tauri いずれも同じ語彙（オブジェクト・コレクションビュー・シングルビュー）で適用する。

## 除外4類型

以下だけが対象外。**この4つに当てはまらないものは無条件で OOUI 必須**。「今回はタスク指向のほうが自然」という判断で逃げない。

| # | 類型 | 例 | なぜ除外か |
|---|-----|---|-----------|
| 1 | 認証/認可フロー | ログイン、サインアップ、2FA、パスワード再設定、招待受諾 | 操作対象となるオブジェクトが存在しない。目的が単一で分岐しない |
| 2 | 不可逆な逐次手続き | 決済、登録ウィザード、オンボーディング | 順序に意味があり、途中で自由に行き来させてはいけない |
| 3 | システム状態ページ | エラー、メンテナンス、権限なし、期限切れ | オブジェクトではなくシステムの状態を伝える画面 |
| 4 | オブジェクトを持たない集計ダッシュボード | KPI サマリ、レポート閲覧専用画面 | 集計値そのものは操作対象のオブジェクトではない |

除外類型でも、**その画面から遷移した先が業務ドメインなら、遷移先には OOUI が適用される**。除外は当該画面に閉じる。

類型 4 の判定に注意する。「ダッシュボード」と呼ばれていても、カード1枚をクリックして個別レコードの詳細に入れるなら、それはコレクションビューであって除外対象ではない。

## OOUI の3手順

新規設計はこの順序で進める。順序を飛ばすと必ずタスク指向に戻る。

### 1. オブジェクト抽出

要件（動詞の羅列）から名詞を取り出す。

```
要件: 「担当者が案件を登録し、進捗を更新して、月末に一覧を出力したい」
        ↓ 動詞を捨てて名詞を拾う
オブジェクト候補: 担当者、案件、進捗（案件の属性か、独立オブジェクトか判断する）
```

判断すること。

- **どれがメインオブジェクトか** — 利用者が主に操作する対象
- **どれがサブオブジェクトか** — 親オブジェクトに従属して存在するもの（案件に紐づくコメント等）
- **どれが属性に落ちるか** — 単独で一覧する意味がないものはオブジェクトにしない
- **多重度** — 親1件に対して子は1件か複数件か

「〜管理」「〜機能」「〜処理」はオブジェクトではない。これが候補に残っていたら抽出が終わっていない。

### 2. ビューとナビゲーションの設計

各オブジェクトに対して2種のビューを対で用意する。

| ビュー | 役割 | 典型的な表現 |
|-------|------|-------------|
| コレクションビュー | オブジェクトの集合を見せ、対象を選ばせる | テーブル、カードグリッド、リスト |
| シングルビュー | オブジェクト1件の詳細を見せ、操作させる | 詳細ページ、詳細パネル |

- ナビゲーション/メニューは**オブジェクトの一覧**にする。機能の一覧にしない
- サブオブジェクトは、独立したトップレベルのメニュー項目にせず、**親のシングルビュー内のコレクションビュー**として置く
- オブジェクト間の参照関係は、参照先のシングルビューへのリンクで表す

### 3. レイアウトパターンの適用

- 新規作成はコレクションビュー上のアクション（「追加」ボタン → モーダルまたはインライン行）
- 編集はシングルビュー内で行う。専用の編集画面を作らない
- 削除はコレクションビューまたはシングルビュー上のアクション
- 一覧が主で詳細が軽いならマスター詳細（左右分割）、詳細が重いなら一覧 → 詳細のページ遷移

## 8項目チェックリスト

設計時・実装時・レビュー時に差分へ機械的に当てる。各項目は Yes/No で答える。No があれば違反。

| # | 検査項目 | NG の具体例 |
|---|---------|-----------|
| 1 | ルート/画面名が名詞で、動詞がパスに出ていない | `/register-user` `/create-project` `/user-management` `/edit-profile` |
| 2 | ナビゲーション/メニューがオブジェクト一覧（名詞）になっている | メニューが「新規登録」「進捗更新」「帳票出力」の並び |
| 3 | 操作順序が「オブジェクト選択 → アクション選択」になっている | メニューでアクションを選んでから対象を選ばせる |
| 4 | コレクションビューとシングルビューが対で存在し、一覧 → 詳細の遷移になっている | 一覧しかなく、詳細が展開行だけで URL を持たない |
| 5 | 新規作成がコレクションビュー上のアクションとして表現されている | `/users/new` が独立画面としてメニューからも直接生えている |
| 6 | CRUD ごとに画面を割っていない | `/users/edit/[id]` `/users/delete/[id]` が別ページとして存在 |
| 7 | コンポーネント名が `<Object><ViewType>` 形式になっている | `RegisterUserForm` `UserManagementPage` `ProjectUpdateModal` |
| 8 | オブジェクト間の参照関係が、親のシングルビュー内のサブオブジェクトコレクションビューとして表現されている | 案件のコメントが `/comments` としてトップレベルに独立している |

`<ViewType>` は `Collection`（集合）と `Detail`（単一）を基本とし、補助的に `Row` `Card` `Panel` を使う。

項目 7 の判定で迷ったときの基準。**プロジェクトが `<Object>`（コレクション）と `<Object>Detail`（シングル）の対で一貫して運用している場合、コレクション側の `Collection` 省略は違反としない**。判定するのは「名前がオブジェクト（名詞）起点になっているか」であって、`Collection` という単語の有無ではない。違反なのは `RegisterUserForm` のようにタスク（動詞）が名前に入っている場合。既存の一貫した命名を、この規約の字面に合わせるためだけに変更しない。

### Next.js（App Router）での対応

ルート構造がそのままビュー構成に一対一で対応する。

```
app/(authenticated)/projects/page.tsx        → Project のコレクションビュー
app/(authenticated)/projects/[id]/page.tsx   → Project のシングルビュー
components/project/ProjectCollection.tsx
components/project/ProjectDetail.tsx
```

### Flutter / 非 Next.js プロジェクトでの読み替え

項目 1 と 7 は語彙を読み替える。

- **項目 1（ルート境界）**: `lib/features/<object>/` を1オブジェクトの境界とみなす
- **項目 7（命名）**: ウィジェット名を `<Object>Collection` / `<Object>Detail` とする

ただし**プロジェクトに既存のディレクトリ規約がある場合は既存規約を優先する**。この規約を新たに持ち込んでディレクトリを再編するのは矯正範囲を超える。判定するのは「名詞になっているか」「オブジェクト単位でまとまっているか」であって、ディレクトリ名の形式そのものではない。

## 既存コードの矯正手順

既存が非 OOUI でも既存パターンに合わせない。**矯正する**。ただし範囲とコミットの規律を守る。

### 範囲は「触ったオブジェクト1つ分」

矯正対象は、変更対象のオブジェクト1つに紐づくもののみ。

- ルート（`app/(authenticated)/<object>/**` または `lib/features/<object>/**`）
- そのオブジェクトのビュー・コンポーネント
- そのオブジェクトの型定義
- そのオブジェクトのテスト（Storybook・Playwright・ユニット）

**隣接オブジェクトには波及させない**。他のオブジェクトが同じ違反をしていても、今回は触らない。アプリ全体やパッケージ全体を一度に矯正しない。

### コミットは必ず分離する

同一 PR 内で、以下の順序でコミットを分ける。

1. **矯正コミット（先行）** — リネーム・ファイル移動・ルート再構成のみ。**挙動は一切変えない**
2. **機能変更コミット** — 本来依頼された変更

矯正コミットを作る前に、対象オブジェクトのテストが通っていることを確認する。矯正コミット後に同じテストを再実行し、**挙動不変であることを確認してからコミットする**。テストが存在しないオブジェクトでは、矯正前後で画面が同一であることを実際に動かして確認する。

1つのコミットにリネームとロジック変更を混ぜない。混ざるとレビューで「これは意図した挙動変更か、リネームの副作用か」が判別できなくなる。

Git の運用（ブランチの切り方、PR の作り方）は `development-delivery` ルール（`rules/development-delivery.md`。Claude Code ではスキル `development-delivery`）に従う。矯正のために PR を分割しない。

## 違反例と修正例

### 例1: CRUD ごとの画面分割

```
Before（違反: 項目 1, 5, 6）
app/users/list/page.tsx
app/users/create/page.tsx
app/users/edit/[id]/page.tsx

After
app/users/page.tsx        → UserCollection（「追加」でモーダルを開く）
app/users/[id]/page.tsx   → UserDetail（この中で編集する）
```

### 例2: タスク名のコンポーネント

```
Before（違反: 項目 7）
RegisterUserForm.tsx / UserManagementPage.tsx / UpdateUserModal.tsx

After
UserCollection.tsx / UserDetail.tsx / UserFormPanel.tsx
```

### 例3: サブオブジェクトのトップレベル化

```
Before（違反: 項目 2, 8）

After
メニュー: [案件]

```

## よくある失敗

- **オブジェクト抽出を飛ばして画面から考え始める** — 必ず名詞の一覧を作ってから画面を設計する
- **「〜管理」をオブジェクトとして扱う** — `UserManagement` はオブジェクトではない。`User` がオブジェクト
- **除外類型を広く解釈する** — 「複雑だからウィザードにしたい」は類型 2 ではない。類型 2 は不可逆な手続きに限る
- **矯正を隣接オブジェクトまで広げる** — PR が読めなくなる。1オブジェクトで止める
- **矯正と機能変更を同じコミットに混ぜる** — レビューが機能しなくなる
- **Flutter プロジェクトに Next.js のディレクトリ規約を持ち込む** — 判定するのは名詞かどうかであって、ディレクトリ名の形式ではない
